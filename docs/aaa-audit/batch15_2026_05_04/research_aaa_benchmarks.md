## 1. Houdini Heightfield System (SideFX)

Houdini is the de-facto reference for terrain authoring at AAA studios — Far Cry 5, Horizon Zero Dawn, Death Stranding, and Ghost of Tsushima all ship Houdini-authored heightfields or Houdini Engine integration. It is the "A grade" for procedural terrain authoring tooling.

### 1.1 Core Architecture

A Houdini heightfield is a **2D volume primitive** — a stack of named float layers sharing the same XZ grid:
- `height` — primary elevation
- `mask` — 0..1 weighting that gates downstream operators
- arbitrary user layers: `flow`, `flowdir`, `sediment`, `debris`, `water`, `bedrock`, `temperature`, `moisture`, `wind`, `slope`, `curvature`, …

Most operators read `mask` as a *second input* and modulate their effect by it. This is the single most important architectural pattern Houdini gets right that VB gets wrong: **every pass is mask-aware, every pass writes to a named layer, and downstream passes read those layers by name** rather than through ad-hoc dicts.

### 1.2 Erosion (HF Erode 3.0, Houdini 21 — 2024 rewrite)

Houdini 21 entirely rewrote its erosion solver. The current parameter model:

| Parameter | Meaning |
|---|---|
| `Erosion Rate` | Removal intensity per simulation step |
| `Flow Force` | Restricts entrainment of harder rock (lower = preserves cliffs) |
| `Erosion Feature Size` | Channel scale; <2-3 voxels → no visible effect |
| `Spread Iterations` | Sediment transport distance / valley fill depth |
| `Weathering Force` | Thermal erosion strength |
| `Freeze at Frame` | Total simulation duration (default = 5 frames) |

**Output layers** generated by the solver:
- `height` (modified)
- `sediment` (deposited soft material)
- `debris` (entrained rock chunks)
- `flow` (water column volume per cell)
- `flowdir` (vector flow direction per cell)

**The key idiom — multi-scale erosion stacking:**
```
HF Noise (large) → HF Erode (Feature Size = 32) →
    HF Distort by Noise → HF Erode (Feature Size = 8) →
        HF Distort → HF Erode (Feature Size = 2)
```
This produces erosion at different *physical scales* — major valleys carved at 32-voxel scale, gullies at 8, rills at 2. Each pass uses the previous pass's outputs as initial state. This is what creates the visual fractal complexity associated with photoreal erosion.

### 1.3 Hydraulic Erosion Algorithm (Mei et al. 2007 pipe model)

Houdini's HF Erode Hydro is widely understood to implement a variant of **Mei, Decaudin, Hu (2007), "Fast Hydraulic Erosion Simulation and Visualization on GPU", Pacific Graphics 2007**. The algorithm is the *de facto* reference and is also implemented in Gaea, World Machine (Flow-Based Erosion device), and Unity's HDRP terrain tools (terrain-tools changelog).

Per-cell state per simulation step:
```
b      bedrock height
d      water depth
s      suspended sediment
fL,fR,fT,fB   outflow flux to 4 neighbours (virtual pipes)
u,v    velocity field (derived from flux)
```

Per-step pipeline:
1. **Water increment**: `d += rainfall * dt`
2. **Flux update** (hydrostatic pressure between adjacent cells):
   `fL_new = max(0, fL_prev + dt * A * g * Δh / l)` where `Δh = (b+d) - (b_left+d_left)`
3. **Flux scaling** to conserve volume: `K = min(1, d * lx*ly / ((fL+fR+fT+fB) * dt))`
4. **Water update**: `d_new = d + dt * (Σf_in - Σf_out) / (lx*ly)`
5. **Velocity field**: `u = (fR_in - fR_out + fL_out - fL_in) / (2 * d * ly)` and same for v
6. **Sediment transport capacity**: `C = K_c * sin(α) * |v|` where α is local slope
7. **Erosion / deposition**: if `C > s` → erode bedrock (`b -= K_s*(C-s)`, `s += K_s*(C-s)`); else deposit
8. **Sediment advection** through velocity field (semi-Lagrangian): `s(p,t+dt) = s(p - v*dt, t)`
9. **Evaporation**: `d *= (1 - K_e*dt)`

Typical published constants (Mei): `K_c = 1.0` (sediment capacity), `K_s = 0.3` (dissolving), `K_d = 0.3` (deposition), `K_e = 0.012` (evaporation), `g = 9.81`.

### 1.4 Thermal Erosion

Houdini's HF Erode Thermal models talus angle / mass wasting:
- For each cell, compute slope to each of 8 neighbours.
- If slope exceeds the *talus angle of repose* (typically 30°-45° for loose material, 60°-85° for rock), redistribute material from this cell to lower neighbours proportional to slope excess.
- Iterated until no cell exceeds the angle (or N steps).

This produces the characteristic scree slopes, talus cones at cliff bases, and rock pile silhouettes.

### 1.5 VEX for Custom Passes

VEX is Houdini's C-like SIMD shader language. The key heightfield pattern is the *Volume Wrangle SOP*: per-voxel code with these built-ins:
- `@P` — voxel world position
- `@height`, `@mask` — current layer values (writable)
- `volumeindex(0, "layer", set(ix,iy,iz))` — read other layers
- `volumegradient(0, "height", v@P)` — analytic gradient (slope)
- `wnoise`, `snoise`, `xnoise`, `pnoise` — noise variants
- `chf("foo")`, `chv("vec")` — UI parameters

This is the architectural slot where VB should expose Python-callable per-voxel hooks, but currently VB's "passes" are coarse-grained Python functions that mutate dicts — there is no per-voxel composition primitive.

## 2. World Machine / Gaea (QuadSpinner)

### 2.1 Gaea — Erosion2 / Wizard / Hydro / MicroErosion / HydroFix

QuadSpinner's headline claim is *resolution-preserving erosion*: a 512² preview matches the 4K-8K final build's macro features. This is achieved by running the simulation at the build resolution but with feature-scale parameters, not by upsampling a low-res result.

The Gaea **Wizard** node is a curated wrapper over the **Erosion2** solver that exposes ~6 high-level parameters (Duration, Rock Softness, Strength, Downcutting, Inhibition, Base Level) instead of Erosion2's 30+. Wizard is the standard entry point for game-ready terrain.

Three core data outputs from Erosion2 / Wizard:
- `Flow` — flow accumulation map (m² of upstream catchment per cell) — the basis for river network masks and silt deposition
- `Wear` — accumulated erosion magnitude — drives "exposed rock" texture mask
- `Deposits` — accumulated sediment thickness — drives "silt/sand/loam" texture mask

**Determinism note**: Gaea's parallel solver is non-deterministic by default; the **Deterministic** toggle forces serial execution for repeatable builds. This matters for game data baking — VB's current "in-process determinism CI" is theatre because it doesn't enforce this kind of explicit determinism mode.

**Specialised nodes:**
- `Hydro` — heavy water-cut river canyons
- `MicroErosion` — sub-meter detail pass (rills, ribbons), runs after macro erosion
- `HydroFix` — repairs flat-bottomed unrealistic valleys produced by upstream nodes

### 2.2 Flow Accumulation — D8 / D-Infinity / MFD

The mathematical basis for Gaea's `Flow` output and Houdini's `flow` layer is **flow accumulation**, a hydrology technique with three flavours:

- **D8** (O'Callaghan & Mark 1984): each cell donates its full upstream area to the *single* steepest of 8 neighbours. Fast, but produces visibly straight, parallel flow lines.
- **D-Infinity** (Tarboton 1997, *Water Resources Research*, "A new method for the determination of flow directions and upslope areas in grid digital elevation models"): donates to the two neighbours straddling the steepest gradient direction, weighted by the gradient angle. Smoother, geomorphologically correct.
- **MFD / Multi-Flow-Direction** (Quinn et al. 1991): donates to *all* downhill neighbours, weighted by slope. Produces broad valley floors.

Most AAA river systems use D-Infinity for the carving phase and MFD for the wetness/moisture phase. **VB has no flow-accumulation layer** in its public passes — a C-grade gap given how universal this is.

### 2.3 World Machine — Tiled Builds

World Machine's tiled build mode renders one tile at a time but each tile renders at *enlarged* extent (the tile + a "blend area" border). The blend area is then merged across tile seams with a configurable blending percentage. This is the gold standard for tile-edge consistency under simulations (erosion, flow) that have non-local effects. **VB currently has no documented blend-area mechanism for cross-tile erosion seams.**

## 3. Ghost of Tsushima (Sucker Punch)

Two key publications: Wohllaib's 2021 GDC talk *"Procedural Grass in Ghost of Tsushima"* (Advanced Graphics Summit) and Patry's SIGGRAPH 2021 *"Real-Time Samurai Cinema"* in the *Advances in Real-Time Rendering* course.

### 3.1 Procedural Grass — Tile Hierarchy

Sucker Punch generates *individual blades of grass on the GPU* via compute shader, with each blade procedurally appearance-randomised. The system uses a **hierarchical tile** structure:

- World is split into large grass tiles (the talk shows ~tens of meters per tile).
- Large tiles subdivide into smaller tiles based on camera distance — closer tiles refine, distant tiles cull.
- Each tile carries a stack of textures:
  - **Terrain height** (for blade root placement)
  - **Material map** (gates which biome's grass grows)
  - **Grass type** (which of N blade profiles to draw)
  - **Clumping factor** (multiplied into a Voronoi-like cell function so blades clump into patches rather than scattering uniformly)
  - **Blade size** (per-cell scalar)
  - **Wind interaction** (pre-baked per-tile wind influence)

**Compute pipeline**: each compute thread = one blade. Thread ID hashes into a deterministic per-blade seed for height variation, lean angle, color jitter. Outputs go through indirect draw calls — only tiles whose visibility-tested AABB intersects the frustum produce vertices.

**Streaming**: a *double-buffer strategy* keeps current + next-ring tile data resident; a worker streams new tiles into the back buffer while the front buffer renders. This avoids hitches when the player crosses tile borders.

### 3.2 Indirect Lighting

Patry 2021 documents a hybrid:
- **Open world**: regular grid of quadratic SH probes — **16 × 16 × 3 per 200 m tile**.
- **Hand-authored locations**: tetrahedral mesh probes streamed dynamically.
- Sky visibility is computed per-frame against the SH probes, then multiplied by sky-SH for time-of-day-aware indirect.

The **200 m tile / 16×16×3 probe density** is the concrete number to benchmark VeilBreakers against if/when we add lighting probe baking.

### 3.3 Specular & Atmosphere

Up to 128 simultaneously-relit cube probes (256² each, with albedo+normal+depth layers, async-relight with SH shadow tracing through depth). Volumetric froxel grid 128×64×64. These are out of scope for terrain but useful when we cite "AAA fidelity" overall.

## 4. Horizon Zero Dawn / Forbidden West (Guerrilla)

### 4.1 GPU-Based Procedural Placement (HZD, GDC 2017)

**Reference**: van der Leeuw & Llopis, "GPU-Based Procedural Placement in Horizon Zero Dawn", Guerrilla Games / GDC 2017.

The HZD "ICE solver" referenced in the task brief is not a publicly named system — what *is* published is the **GPU procedural placement** pipeline that operates on World Data (also called "ecotopes"). Its conceptual structure:

- **Stamps** — an artist-authored disc of placement rules applied at a world-space anchor. Stamps have priority (foreground stamps mask out background ones).
- **Density fields** — 2D textures per ecotope: `tree_density`, `bush_density`, `grass_density`, `rock_density`. Multiplied by environmental masks.
- **Environmental rules** — per asset prototype:
  - Slope range (e.g., trees: 0°-25°; cliffs: 60°-90°)
  - Altitude range
  - Distance-to-water
  - Distance-to-road
  - Soil type / biome tag
- **Poisson-disk sampling** on the GPU using a tile-based dart-throwing variant. Each tile generates candidates from a hashed seed; candidates are accepted if they pass all environmental rules and are at least the asset's footprint distance from previously-accepted candidates.
- **GPU compute** runs at world-streaming time (when a tile loads) — placement is *not* baked offline. This makes the world tweakable without re-baking.

### 4.2 World Data ("ecotope") System

Per a 2017 Guerrilla blog, *"At the flick of a switch the team could turn a dense, palm-filled, and humid jungle to a sparse, dry, cacti-filled desert environment."* — an ecotope swap remaps every density field, every asset prototype list, every environmental rule, without touching the heightfield. **This is what VeilBreakers' biome system aspires to but currently has fragmented across three biome-name vocabularies (per Batch 13 audit).**

### 4.3 Decima Visibility (HZD, GCAP 2017)

- World decomposed into **StaticTiles** (sometimes literal spatial tiles, sometimes scenes like settlements).
- Each tile is *flat GPU buffers* (object transforms, AABBs, LOD bracket lists) plus a CPU-side cluster list.
- Per frame: CPU job tests tile + cluster visibility; for every visible cluster a GPU compute job tests per-mesh LOD selection. *"A leaf is visible iff both parent and child LODs are selected"* — tight LOD hysteresis prevents pop-in.

### 4.4 Forbidden West — Deferred Texturing for Foliage (GDC 2022)

McLaren 2022, *"Adventures with Deferred Texturing in Horizon Forbidden West"*. Foliage and alpha-tested geometry pipeline:
1. **Visibility buffer prepass** — writes triangle ID + barycentrics, no shading.
2. **Tile analysis** (compute) — bins triangles into screen tiles; classifies tiles by material/shading complexity.
3. **Shading** (compute, per-tile) — fetches material attributes, runs per-pixel shading, writes to G-buffer.

Crucially: runs on **async compute pipes** so it overlaps with rasterised G-buffer + cascaded shadow map generation. This is also where **software variable rate shading** is implemented — a 1×1, 1×2, 2×2, 2×4 etc. block size selected per tile based on motion + complexity.

For VB this is a future renderer-side concern; the relevant takeaway for terrain is that **foliage and terrain rendering are decoupled in shipping AAA** and use different pipelines.

### 4.5 Streaming + Jolt + Volumetrics (HFW, GDC 2022)

- Switched to **Jolt Physics** — 2× simulation frequency, lower memory than Havok.
- **Volumetric superstorms** — extended cloud system with internal lighting, lightning flashes, tornadic structure.

Tangentially relevant: the cloud system is where wind vector fields get authored at world scale; they are then sampled by the grass/foliage shaders.

## 5. Red Dead Redemption 2 (Rockstar / RAGE)

Primary reference: **imgeself.github.io graphics study (2020)** — frame-capture-based reverse-engineering with corroboration from publicly leaked tech notes.

### 5.1 Mud / Footprint Accumulation

A persistent **2048 × 2048 R16_UNORM "mud map"** accumulates:
- Human footprints
- Horse hoofprints
- Wagon wheel tracks
- Drag trails

Every frame the mud map is sampled in the terrain shader as a *parallax occlusion mapping (POM)* heightfield, producing genuine geometric depression where footprints fall.

### 5.2 G-Buffer Layout (Terrain-Relevant)

| RT | Format | Contents |
|---|---|---|
| GBuffer0 | RGBA8_SRGB | Albedo |
| GBuffer1 | RGBA8_UNORM | Surface normal |
| GBuffer2 | RGBA8_UNORM | Reflectance, smoothness, metallic |
| GBuffer3 | RGBA8_UNORM | Cavity (AO) |
| GBuffer5 | D32S8 | Reversed-Z depth |

A separate terrain depth prepass runs before full G-buffer fill to enable Hi-Z occlusion of subsequent terrain layers.

### 5.3 Layer Blending & Wetness

The RDR2 terrain shader uses **height-based (POM) layer blending**, not the linear-weighted splatmap blend that Unity's default terrain shader uses. Each layer carries its own height map; the blend at a pixel uses `max(layer_a.h + weight_a, layer_b.h + weight_b)` — this produces sharp, geomorphic transitions (e.g., wet mud peeking through dry crust where the crust's height is lower).

Wetness is a *separate* world-state texture sampled by every terrain pixel; rain raises the wetness, sun + wind lower it, with spatial variation from cover (tree LOD shadow proxies) and slope (puddles in low spots).

The shared heightmap doubles as input for shadow self-occlusion and texture blending — explicitly noted as a quality-vs-memory tradeoff.

### 5.4 Road Networks

RDR2 roads were authored by hand on top of a procedural road-cost layer (slope + water + biome) — not procedurally generated end-to-end. **Far Cry 5 is the better reference for fully procedural road generation** (§6 below).

## 6. Unreal Engine 5 — Nanite Landscape + World Partition

### 6.1 Nanite Landscape (UE 5.3+)

- Landscape components are converted to Nanite meshes at cook time.
- Nanite handles seamless LOD (no LOD pop, no skirt geometry) by streaming clusters of triangles per camera tile.
- Requires **World Partition** for frustum culling — without WP the entire landscape is loaded and Nanite cluster culling is a no-op per Epic forum guidance.
- Material layers on Nanite Landscape are limited to the same per-component set (typically 6-8 layers active per landscape component).

### 6.2 Virtual Heightfield Mesh (VHM)

- An *experimental* (UE 5.0-5.7) plugin that creates an endlessly tessellating displacement mesh driven by an RVT (Runtime Virtual Texture).
- Replaces the old (deprecated in UE 5) hardware-tessellation + displacement workflow.
- Setup: enable VHM plugin → enable Virtual Texture Support → create RVT Volume → output `WorldPosition.z + Displacement` into the RVT → spawn VHM actor sampling the RVT.
- Known issues: flickering at distant tiles, blurry RVTs at low MIP.

### 6.3 World Partition Cell Sizing

- Default grid cell size: **2 × 2 km** (200,000 cm).
- Recommended cell size = **landscape component size × 1× or 0.5×** (in cm), minus 1.
- For a 8129² landscape (max recommended), max grid is 32 × 32 km (1024 km²) but performance degrades at that extreme.
- **HLOD generation is required** for Nanite + WP; failure to bake HLODs causes the World Partition + Nanite + Landscape combo to crash (Epic forums document this for 5.11+).

### 6.4 Runtime Virtual Texturing (RVT)

The "secret weapon" for AAA-quality terrain in UE5:
- Bake heavy material costs (decals, splatmaps, road overlays) into RVT pages.
- Sample the RVT in the terrain material instead of recomputing layer blends per pixel per frame.
- Foliage shaders sample the same RVT to color-match the terrain underneath (critical for grass-meets-dirt seams).

## 7. Unity HDRP Terrain (VeilBreakers's Target)

### 7.1 Hard Limits — HDRP

- **8 terrain layers per tile, single-pass.** Adding a 9th renders it black at runtime. (`docs.unity3d.com/Manual/class-TerrainLayer.html`).
- Splatmaps stored in `_TerrainData.alphamapTextures[]` — each texture is `RGBA32` with up to 4 layer weights packed per texture; 8 layers = 2 splatmap textures.
- TerrainData is *shareable between HDRP and URP* — but the terrain *material* is not.

### 7.2 TerrainData Binary Layout (Unity's Internal Format)

Unity does not publish the on-disk binary, but the runtime API (`TerrainData.GetHeights`, `GetAlphamaps`, `GetDetailLayer`) tells us the canonical structure:

| Section | Type | Notes |
|---|---|---|
| Heightmap | float[heightmapResolution, heightmapResolution] | Values 0..1, scaled by `terrainData.size.y` at sample time |
| Holes | bool[heightmapResolution-1, heightmapResolution-1] | NEW in 2019.3+ — per-quad hole mask |
| Alphamaps | float[alphamapResolution, alphamapResolution, layerCount] | Splatmaps; sum-to-1 across layer axis |
| Details | int[detailResolution, detailResolution] per detail prototype | Per-cell instance count for each detail |
| Tree instances | TreeInstance[] | Position, prototype index, height/width scale, color |

### 7.3 Resolution Recommendations for AAA-Quality 500 m Tile

For a **500 m × 500 m** tile targeting AAA visual fidelity:

| Setting | Recommended | Rationale |
|---|---|---|
| Heightmap Resolution | **1025 (1024+1)** | ~0.49 m / sample → matches RDR2-class terrain detail; doubles draw calls vs 513 |
| Control Texture (Splatmap) Resolution | **1024 or 2048** | 1024 = 0.49 m / splat pixel; 2048 needed if any layer has sub-meter detail |
| Base Map Resolution | **1024** | Used beyond `basemapDistance`; must match splatmap or you get a visible LOD seam |
| Detail Resolution | **2048** | 0.244 m / detail cell → enough density for grass/pebbles |
| Detail Resolution Per Patch | **16** (recommended), tuneable 8-128 | 16² = 256 cells per draw call; lower = more draws but better culling |

**The "must be 2^n+1" rule** for heightmap and "must be 2^n" for splatmap is a hard Unity constraint. 513-vs-1025 is the most common AAA decision: 513 (~1 m) for budget tiles, 1025 (~0.5 m) for hero tiles.

A bug caveat documented by Unity: **terrain shape doesn't match the collider when heightmap < 513**, which forces 513 as the absolute floor.

### 7.4 WindZone × Terrain Detail Behaviour (Critical Gotcha)

**WindZones do NOT apply to terrain grass details.** This is a Unity-specific gotcha that catches people. Grass wind is configured in TerrainData via `wavingGrassStrength`, `wavingGrassAmount`, `wavingGrassSpeed`, `wavingGrassTint` — these are TerrainData properties, edited via the gear icon → wind settings.

WindZones DO apply to:
- SpeedTree assets (placed as terrain trees)
- Tree prototypes that read `_WindAnimation` in their shaders
- Detail prototypes only if their custom shader explicitly samples `_TerrainEngineBendTree`

For SpeedTrees: `Main` strength, `Turbulence` randomness, `Pulse Magnitude` and `Pulse Frequency` for gust modeling.

This bifurcation is why VB's wind-related code paths must explicitly handle "is this a grass detail or a tree?" — VB currently does not, per the foliage-attachment audit finding.

### 7.5 Recommended File for VeilBreakers — TerrainData Authoring

The pattern AAA Unity teams use:
1. Author terrain in Houdini or Gaea → export 16-bit RAW heightmap + per-channel splatmap PNGs + density-field PNGs.
2. Import via custom `AssetPostprocessor` → instantiate `TerrainData`, call `SetHeights`, `SetAlphamaps`, `SetDetailLayer`, `SetTreeInstances`.
3. Bake HLODs via terrain HLOD package.
4. Stream by spawning/despawning Terrain GameObjects from Addressables.

VB currently bakes via NMX/OBJ exports rather than authoring `TerrainData` directly — that is a renderer-side gap (Batch 12 finding), not a terrain-physics gap.

## 8. Far Cry 5 (Ubisoft Montreal) — Houdini-Driven Pipeline

Reference: **Carrier 2018, "Procedural World Generation of Far Cry 5", GDC 2018** + Houdini HIVE Utrecht talk.

This is the most complete public AAA recipe for Houdini-driven open-world generation.

### 8.1 Inputs — "Biome Recipes"

Each biome recipe takes as input layers:
- **Heightmap** (artist-painted base)
- **2D biome paint mask** (artist marks "here is jungle, here is desert")
- **Slope** (computed from heightmap)
- **Altitude** (raw heightmap value)
- **Latitude / Longitude** (for global climate gradient)
- **Wind vector map** (drives fallen-leaf orientation, tree lean)
- **Curvature** (concavity → wet hollows, convexity → exposed ridges)
- **Distance-to-water** (computed from a freshwater-network pass)
- **Cliff erosion lines** (procedural — extracted from the height + slope)

### 8.2 Pipeline Order

1. **Terraforming** — apply hand-painted heightmap, run multi-scale erosion.
2. **Freshwater definition** — flow-accumulation → river network → carve channels into heightmap.
3. **Cliff generation** — stamp rock chunk meshes along slope > threshold.
4. **Biome painting** — generate biome mask from inputs above.
5. **Vegetation spawning** — each biome's recipe runs species *viability* function; samples Poisson-distributed candidates; accepts based on viability score.

### 8.3 Roads

- Splines drawn manually on the cost surface.
- Road clears vegetation (paints exclusion mask) and stamps in road mesh + road texture layer.
- Manual asset placement (houses, vehicles) follows.

**This is the canonical 'A-grade' road workflow VB should target** — A* on a cost surface (slope, water, rock) for fully procedural, manual splines on the same cost surface for hero areas. VB currently has *two disconnected road systems* (Batch 13) and the road pass is *unregistered* — both are blocking issues.

### 8.4 Key Architectural Pattern

> "Asset placement needs to be consistent with the terrain topology, and the biomes procedural system should be able to simulate natural phenomena."

Every asset placement decision in Far Cry 5 reads from terrain-derived layers (slope, curvature, moisture). **Nothing is placed via "random in box".** This is the defining gap between AAA and VeilBreakers's current `random.Random` scatter — there is no "viability function" architecture in VB.

## 9. The Witcher 3 — REDengine 3 Streaming (Reference, GDC 2014)

Gollent 2014, *"Landscape Creation and Rendering in REDengine 3"*. Useful only as a streaming-architecture reference.

- Novigrad area: **46 × 46 tiles of 512 × 512 each** — total 23552 × 23552 elevation samples.
- **5 clipmap levels** for streaming.
- Three streamed clipmaps:

## 10. Domain Warping — The Noise Stack VB Is Missing

**Reference**: Inigo Quilez, "Domain Warping" (iquilezles.org/articles/warp/).

The basic equation: `f(p)` becomes `f(p + h(p))` where `h` is itself an fBm. Iterated:
- 1st pass: `q = fbm(p)`
- 2nd pass: `r = fbm(p + q)`
- 3rd pass: `f = fbm(p + r)`

This produces the swirling, organic, geomorphic patterns that make AAA terrain look "natural" rather than "Perlin-y". It is the single highest-leverage upgrade VeilBreakers could make to its noise stack.

**Multifractal** (Musgrave et al.): scale each octave's amplitude by the *previous* octave's value so that high terrain gets sharper detail and low terrain gets softer detail — produces the "rougher peaks, smoother valleys" effect of real geology.

**Voronoi / Worley** (cellular noise): produces the cell structures used for stone tiling, alpine shattered cliffs, hexagonal columnar joints (basalt). Combined with domain warping, Voronoi → "Voronoise" produces the cracked-mud / tessellated-rock patterns of high-end Substance materials.

The recommended VB noise stack:
```
base_height = ridged_multifractal(domain_warp(p, fbm_offset), octaves=8)
            + 0.3 * voronoise(p * 0.01)            # cell-scale plate boundaries
            + 0.05 * fbm(p * 4.0, octaves=4)        # sub-meter roughness
```

### 12.1 Mei 2007 Hydraulic Erosion Step (NumPy-ready)

```python
def hydraulic_step(b, d, s, fL, fR, fT, fB,
                   rainfall=0.012, dt=0.1,
                   Kc=1.0, Ks=0.3, Kd=0.3, Ke=0.012,
                   g=9.81, lx=1.0, ly=1.0, A=1.0):
    # 1. Rain
    d = d + rainfall * dt
    # 2. Flux update (per direction)
    h = b + d
    dhL = h - np.roll(h, 1, axis=1); dhL[:,0] = 0
    fL = np.maximum(0.0, fL + dt * A * g * dhL / lx)
    # ... fR, fT, fB symmetrically ...
    # 3. Conservation scaling
    sumF = fL + fR + fT + fB
    K = np.minimum(1.0, d * lx * ly / np.maximum(sumF * dt, 1e-9))
    fL *= K; fR *= K; fT *= K; fB *= K
    # 4. Water update
    inflow = (np.roll(fR,1,axis=1) + np.roll(fL,-1,axis=1)
            + np.roll(fB,1,axis=0) + np.roll(fT,-1,axis=0))
    outflow = sumF
    d_new = d + dt * (inflow - outflow) / (lx * ly)
    # 5. Velocity
    u = (np.roll(fR,1,axis=1) - fL + fR - np.roll(fL,-1,axis=1)) / (2.0 * np.maximum(d_new, 1e-6) * ly)
    v = (np.roll(fB,1,axis=0) - fT + fB - np.roll(fT,-1,axis=0)) / (2.0 * np.maximum(d_new, 1e-6) * lx)
    # 6. Sediment capacity
    slope = compute_slope_sin(b)
    C = Kc * slope * np.sqrt(u*u + v*v)
    # 7. Erode/deposit
    erode = np.where(C > s, Ks * (C - s), 0.0)
    deposit = np.where(C <= s, Kd * (s - C), 0.0)
    b -= erode - deposit
    s += erode - deposit
    # 8. Sediment advection (semi-Lagrangian)
    s = advect_semilagrangian(s, u, v, dt)
    # 9. Evaporation
    d_new = d_new * (1.0 - Ke * dt)
    return b, d_new, s, fL, fR, fT, fB
```

### 12.2 D-Infinity Flow Accumulation (Tarboton 1997)

```python
def d_inf_flow_accumulation(h, cell_area=1.0):
    """Returns flow accumulation (m^2 of upstream catchment) per cell."""
    H, W = h.shape
    # 1. For each cell, compute steepest direction angle in [0, 2pi)
    direction = np.zeros_like(h)
    slope = np.zeros_like(h)
    for facet in range(8):
        # Tarboton's 8 triangular facets between cardinal+diagonal pairs
        s, a = facet_steepest_descent(h, facet)
        mask = s > slope
        direction[mask] = a[mask]; slope[mask] = s[mask]
    # 2. Process cells in descending elevation order
    order = np.argsort(-h.ravel())
    accum = np.full_like(h, cell_area)
    for idx in order:
        r, c = divmod(idx, W)
        # 3. Distribute this cell's accum to two neighbours
        # straddling direction[r,c], weighted by angle alpha
        n1, n2, w1 = neighbours_for_angle(direction[r,c])
        if in_bounds(r+n1[0], c+n1[1], H, W):
            accum[r+n1[0], c+n1[1]] += accum[r,c] * w1
        if in_bounds(r+n2[0], c+n2[1], H, W):
            accum[r+n2[0], c+n2[1]] += accum[r,c] * (1 - w1)
    return accum
```

### 12.3 Domain-Warped Ridged Multifractal (Quilez + Musgrave)

```python
def ridged_mf(p, octaves=8, lacunarity=2.0, gain=0.5, offset=1.0):
    f = 1.0; a = 1.0; sum_ = 0.0; prev = 1.0
    for _ in range(octaves):
        n = offset - abs(perlin(p * f))
        n = n * n
        sum_ += n * a * prev
        prev = n
        f *= lacunarity; a *= gain
    return sum_

def domain_warped_terrain(p):
    q = vec2(fbm(p), fbm(p + vec2(5.2, 1.3)))
    r = vec2(fbm(p + 4.0*q), fbm(p + 4.0*q + vec2(8.3, 2.8)))
    return ridged_mf(p + 4.0*r, octaves=8)
```

### 12.4 Bridson Fast Poisson-Disk (replacement for `random.Random` scatter)

```python
def bridson_poisson(width, height, r, k=30, seed=0):
    """Maximally-Poisson-disk-spaced points; r = min separation."""
    rng = np.random.default_rng(seed)
    cell = r / math.sqrt(2)
    grid = -np.ones((int(width/cell)+1, int(height/cell)+1), dtype=int)
    samples = []; active = []
    p0 = (rng.random()*width, rng.random()*height)
    samples.append(p0); active.append(0)
    grid[int(p0[0]/cell), int(p0[1]/cell)] = 0
    while active:
        i = rng.choice(active); cx, cy = samples[i]
        for _ in range(k):
            theta = rng.random()*2*math.pi
            rad = r * (1 + rng.random())
            nx, ny = cx + rad*math.cos(theta), cy + rad*math.sin(theta)
            if not (0 <= nx < width and 0 <= ny < height): continue
            gx, gy = int(nx/cell), int(ny/cell)
            ok = True
            for dx in range(-2, 3):
                for dy in range(-2, 3):
                    nb = grid[gx+dx, gy+dy] if (0<=gx+dx<grid.shape[0] and 0<=gy+dy<grid.shape[1]) else -1
                    if nb >= 0:
                        sx, sy = samples[nb]
                        if (sx-nx)**2 + (sy-ny)**2 < r*r:
                            ok = False; break
                if not ok: break
            if ok:
                samples.append((nx,ny)); active.append(len(samples)-1)
                grid[gx,gy] = len(samples)-1; break
        else:
            active.remove(i)
    return samples
```

### 12.5 Far Cry 5 Style Viability Function (Vegetation)

```python
def viability_score(species, slope_deg, altitude_m, moisture, water_dist, biome_id):
    s = 1.0
    s *= ramp(slope_deg, species.slope_min, species.slope_max)
    s *= ramp(altitude_m, species.alt_min, species.alt_max)
    s *= ramp(moisture, species.moisture_min, species.moisture_max)
    if species.requires_water:
        s *= 1.0 - clamp01(water_dist / species.max_water_dist)
    if biome_id not in species.allowed_biomes:
        s = 0.0
    return s

def scatter_with_viability(species, candidates, accept_threshold=0.3):
    accepted = []
    for p in candidates:  # candidates from Bridson
        v = viability_score(species,
                            slope_at(p), altitude_at(p),
                            moisture_at(p), water_dist_at(p),
                            biome_at(p))
        if v >= accept_threshold and random() < v:
            accepted.append((p, v))
    return accepted
```
