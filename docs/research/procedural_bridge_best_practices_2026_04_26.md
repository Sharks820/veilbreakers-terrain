# Procedural Bridge Best Practices - 2026-04-26

This note converts the bridge research pass into implementation rules for the
Veilbreakers terrain generator. It is focused on bridge-to-path transitions,
material-driven bridge form, and visual QA requirements.

## Sources Checked

- SideFX Houdini Sweep SOP: backbone curve plus cross-section surface generation; supports curve attributes and multiple cross-sections.
  https://www.sidefx.com/docs/houdini/nodes/sop/sweep.html
- SideFX Houdini Copy to Points SOP: point attributes such as orientation and scale drive repeated geometry modules.
  https://www.sidefx.com/docs/houdini/nodes/sop/copytopoints-.html
- Blender Geometry Nodes Curve to Mesh and Instance on Points concepts: bridge decks, rails, posts, and supports should be generated from curves plus instance-point streams.
  https://docs.blender.org/manual/en/latest/modeling/geometry_nodes/curve/operations/curve_to_mesh.html
  https://docs.blender.org/manual/en/latest/modeling/geometry_nodes/instances/instance_on_points.html
- Unity Splines Spline Extrude: spline-driven mesh generation updates related objects when the source spline changes and exposes road-style extrusion parameters.
  https://docs.unity.cn/Packages/com.unity.splines%402.7/manual/extrude-component.html
- Unreal Spline Mesh Component: spline-deformed static mesh pieces use start/end positions and tangents, which maps well to modular bridge sections.
  https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/SplineMeshComponent
- AASHTO/FHWA Bridge Aesthetics Sourcebook excerpts: visual quality should come from the proportions and shapes of structural members first, not decorative afterthoughts.
  https://store.transportation.org/Common/DownloadContentFiles?id=887

## Generator Rules

1. Build from a centerline contract, not from a single stretched mesh.
   The bridge span is the source curve. Deck, rails, arch ribs, ropes, posts,
   piers, and approach transitions are derived from that curve.

2. Use modular spacing.
   Wood planks, rope posts, rail posts, stone voussoirs, piers, and arch bays
   must be generated by module counts based on span length. Longer bridges add
   modules and supports instead of scaling one primitive.

3. Let material family control structure.
   Wood should produce timber planks, stringers, posts, rails, and bracing.
   Rope should produce a sagging pedestrian bridge. Stone should produce deck,
   parapets, arch ribs, abutments, and, for long spans, repeated viaduct bays.

4. Require approach transitions.
   Every bridge contract needs approach-transition material on both banks. The
   road/path width must match the deck width before the bridge begins, and
   terrain-only paths still need bridge contract spans when they cross water.

5. Separate structural truth from visual style.
   `bridge_clearance_m`, `water_depth_m`, `bridge_span_m`, `support_count`,
   `arch_count`, and `material_slots` are required metadata. Visual decoration
   can vary, but those contract fields cannot lie or disappear.

6. Validate from cameras.
   Bridge QA needs an overhead view, approach view, side/waterline view, and
   deck-level view. The prompt checklist must confirm bridge type, path
   continuity, water clearance, bank transitions, material match, and visible
   support logic.

## Implementation Status

- `generate_terrain_bridge_mesh(style="wood")` now resolves to a timber-beam
  profile with timber material slots, module count, support count, and approach
  transition metadata.
- `generate_terrain_bridge_mesh(style="stone")` now resolves to `stone_arch`
  or `stone_viaduct` based on span/width. Long stone spans generate repeated
  arch bays and supports.
- Road/path contracts now preserve bridge spans for terrain-only dirt/path/trail
  crossings when water level is present.

## Next Required Upgrade

The next bridge pass should move from metadata-rich mesh generation to a full
`BridgeGenerationContract` object with:

- `centerline_points`
- `approach_start` and `approach_end`
- `deck_profile`
- `support_points`
- `material_family`
- `material_slots`
- `visual_qa_cameras`
- `engine_export_hints`

That object should be consumed by Blender mesh generation and Unity export
instead of duplicating bridge assumptions in multiple handlers.
