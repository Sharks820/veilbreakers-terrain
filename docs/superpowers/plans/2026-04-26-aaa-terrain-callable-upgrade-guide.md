# AAA Terrain Callable Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade VeilBreakers terrain generation so terrain, water, foliage, materials, cliffs, caves, roads, and export systems follow proven procedural terrain practices: layered heightfield channels, hydrology-derived masks, point-cloud scatter data, normalized material weights, debuggable callable routing, and output proof. The system must stop accepting one-shot handmade scene scripts as the primary terrain architecture.

**Architecture:** Treat every terrain result as a pipeline product with named channels and callable provenance. A generation request flows through canonical passes, emits a `TerrainMaskStack` or equivalent artifact, writes typed scatter point tables and export manifests, then runs visual and contract QA. Hand-authored helpers may exist only as library functions behind registered handlers, documented pass definitions, and tests.

**Tech Stack:** Python terrain handlers, Blender integration handlers, MCP command dispatch, NumPy/SciPy-style heightfield math where available, pytest contract tests, Blender runtime tests where needed, Unity export manifests, existing callable census and verification reports.

## Core Finding

The major quality problem is not that the repo lacks terrain functions. The repo has many of the pieces: hydrology, cliffs, material layers, foliage cataloging, LODs, Unity export, visual QA, road networks, waterfalls, weathering, ecotones, and Blender safety utilities. The failure is that too many rich callables are not canonical, not wired into production handlers, or not protected by output contracts. This causes the system to fall back to scattered handmade geometry, weak masks, shallow water surfaces, slope-only materials, copy-pasted foliage, and disconnected waterfall visuals.

The implementation must therefore prioritize:

- Canonical pass routing before adding new generation tricks.
- Channel contracts before aesthetic tuning.
- Hydrology and material coupling before shader polish.
- Point data and scatter provenance before more assets.
- Runtime/export proof before claiming AAA quality.

## Added Research Delta: World Creator

World Creator needs more weight in implementation than the first version of this plan gave it. Its official docs imply three separate export contracts that our system should copy:

- Dense object/details export: `DetailInfo.json` plus per-layer splatmaps for grass, small rocks, and high-count procedural scatter.
- Exact instance export: `InstanceInfo.json` plus per-layer point-cloud CSV containing translation, scale, quaternion rotation, gradient, and seed.
- Spline export: `.dae` export for Path and River layers, which maps directly to our road, river, and path feature contracts.

World Creator river docs also matter. River generation analyzes terrain, calculates flow paths, places springs/nodes, assigns river types from hydrological properties, and exposes valley shape controls such as width, depth, floodplain area, and wall shape. This directly upgrades our water plan:

- `_water_network.py` should output spring/node/segment graphs, not only raster masks.
- `build_braided_polylines` and `compute_shreve_orders` are not optional extras; they map to World Creator-style multi-channel river types.
- `terrain_waterfalls.py` should consume the same graph so waterfalls, plunge pools, braided rivers, and lakes are one hydrology system.
- Export should support both dense procedural splatmaps and exact point instances, depending on object type.

The first implementation foothold is now present in `veilbreakers_terrain/handlers/terrain_scatter_points.py`. It adds a canonical `ScatterPointTable` and a World Creator-style instance point-cloud converter. This is the correct route for trees, foliage, rocks, boulders, logs, stumps, shrubs, water foliage, and environmental props because it records exact point data instead of scattering untraceable mesh copies.

Required scatter-point fields:

- position in world meters
- normal
- orientation quaternion
- scale
- prototype id
- species id
- biome id
- density/gradient
- seed
- slope
- height
- mask provenance
- LOD bucket
- wind profile
- source layer
- exact-instance vs dense-detail mode

The rule for all future scatter work is: scatter callables may generate points, masks, density fields, and manifests; asset callables may generate or validate prototypes; Blender/Unity callables may instantiate/export those points. No production scatter path should directly place opaque duplicated meshes without a `ScatterPointTable`.

## Added Research Delta: Houdini Terrain and Texturing

Houdini is the strongest reference for how our terrain internals should be organized because it treats terrain as heightfield volumes with named layers, not as a final mesh first. The official docs reinforce these implementation rules:

- The base height layer remains distinct from masks and custom layers.
- Erosion outputs such as `debris`, `sediment`, and `flow` become reusable texture/material layers.
- Texture layers are masks copied and stored for reuse, not one-off color decisions.
- HeightField Mask by Feature derives masks from height, curvature, direction, occlusion, and other terrain features.
- HeightField Scatter emits terrain points with seed, orientation, normals, slope direction, footprint/radius, and point count or density controls.
- HeightField Output exports layers as deep rasters, packed RGBA rasters, or tiled maps.

Callable impact:

- `TerrainMaskStack` should become our Houdini-style layer carrier.
- `_terrain_erosion.py`, `_water_network.py`, and `terrain_cliffs.py` must emit reusable physical layers, not only mutate height.
- `terrain_materials.py` must consume those layers as texture masks.
- `environment_scatter.py` must treat scatter points like Houdini scatter points: deterministic seed, normal, orient, yaw/up jitter, slope alignment, footprint, and mask provenance.
- `terrain_unity_export.py` must support packed RGBA layer exports and per-layer image exports.
- `terrain_visual_qa.py` must render debug views for height, flow, debris, sediment, wetness, slope, curvature, material weights, and scatter density.

This also clarifies the "terrain generator" confusion: Houdini is not just a terrain generator. It is a procedural DCC system whose heightfield toolset is a reference architecture for terrain layers, masks, scatter points, material layering, export, and VFX coupling.

## Added Research Delta: Blender MCP and AI-to-Blender Control

Blender MCP is not official Blender Foundation guidance and should not define terrain best practice. It is still relevant because it demonstrates a working AI-to-Blender execution pattern:

- MCP server plus Blender add-on.
- Scene inspection tools.
- Object creation/modification tools.
- Material and lighting commands.
- Viewport screenshot capture.
- Asset retrieval through Poly Haven-style APIs.
- Optional AI model generation integrations.
- Arbitrary Python execution, which is powerful but unsafe as a default production surface.

Our Blender implementation should therefore avoid "AI writes arbitrary `bpy` script" as the normal terrain workflow. The correct translation is:

- Provide small, typed recipe tools that agents can call safely.
- Keep raw Python execution behind an explicit debugging/admin path.
- Log every recipe call with input payload, affected objects, generated attributes, output paths, and screenshots.
- Add scene-read validators that prove Blender contains the expected heightfield mesh, named attributes, water surfaces, scatter instances, material layers, and camera/render outputs.

Required additional Blender/MCP recipe tools:

- `terrain_read_scene_contract`
- `terrain_build_heightfield_mesh_from_channels`
- `terrain_apply_named_attribute_layers`
- `terrain_apply_world_creator_pointcloud`
- `terrain_apply_detail_splat_scatter`
- `terrain_apply_substance_style_material_stack`
- `terrain_capture_viewport_and_channel_debug`
- `terrain_export_blender_qa_manifest`

## Added Research Delta: Maya, Bifrost, and XGen

Maya matters here because Autodesk positions Bifrost as graph-based procedural content creation for film, TV, and games, including procedural scatter/instancing, USD workflows, geometry nodes, simulations, particles, waves, snow, and MPM-style effects. XGen matters because it models surface-bound primitive descriptions for hair, grass, plants, and instanced geometry.

Translate those practices into our repo as follows:

- Scatter should be graph-like and reusable, not a local loop inside one handler.
- Density weights must be explicit input fields, not hidden random thresholds.
- Point outputs must retain sampled geometry locations so later passes can query height, slope, biome, wetness, and material context.
- Foliage/grass systems need descriptions/collections by species or vegetation role, not one undifferentiated scatter set.
- USD-style thinking means export manifests should identify prototypes, instances, transforms, material bindings, variants, and payload paths.

Callable impact:

- `environment_scatter.py` and `_scatter_engine.py` should own graph-level scatter contracts.
- `terrain_foliage_catalog.py` should own XGen/SpeedTree-style species descriptions and prototype metadata.
- `terrain_unity_export.py` should export instance/prototype/material bindings separately.
- `blender_capability_bridge.py` should be treated like a DCC adapter, not the procedural source of truth.

## Added Research Delta: Adobe Substance 3D

Adobe Substance references should drive the material portion of the terrain plan. The core practice is not "make a color texture"; it is a material graph with explicit PBR/geometry outputs:

- base color
- roughness
- metallic where relevant
- ambient occlusion
- normal
- height/displacement
- height scale and height level
- curvature and AO-derived masks
- height blending and material height blending
- weathering masks such as dirt, dust, leaks, moss, rock weathering, and edge wear
- tiling/safe transforms

Callable impact:

- `terrain_materials_ext.compute_height_blended_weights` becomes a mandatory production input, not an orphan.
- `terrain_materials.py` and `terrain_materials_v2.py` should emit PBR channel manifests, not only layer labels/colors.
- `terrain_stochastic_shader.py` must consume normalized material layers and PBR channel provenance.
- `terrain_macro_color.py` should be downstream from material physics, not a substitute for it.
- Visual QA should inspect roughness/normal/height/AO presence for ground, cliffs, wet rock, cave mouths, riverbeds, and talus.

## Added Research Delta: Quixel, Megascans, and Terrain Texture QA

Quixel/Megascans and Mixer matter because our repo already has `terrain_quixel_ingest.py`, and because Quixel's official material docs state the same PBR requirements as Substance from a scanned-asset perspective:

- Albedo/base color carries surface color.
- Roughness/gloss controls microfacet reflection width.
- Normal maps simulate surface-lighting detail without changing geometry.
- Displacement maps move the surface along normals when the engine supports it.
- Ambient occlusion stores local occlusion/shadowing information.
- Curvature stores convexity/concavity information useful for wear, dirt, and edge effects.
- Mixer layer sets and mask stacks exist so materials can be blended and targeted across multiple texture sets.

Callable impact:

- `terrain_quixel_ingest.py` should become one input provider into the generic `TerrainTextureLayerStack`, not a standalone material shortcut.
- `terrain_materials_ext.py` should validate that material layers have the required PBR map set or an explicit fallback reason.
- `terrain_validation.py` should fail flat/washed-out materials when normal, roughness, height/displacement, or AO are missing for AAA profiles.
- `terrain_unity_export.py` must preserve packed texture-channel semantics, including mask maps and height data used by Unity height-based terrain blending.
- Blender import should mark non-color data correctly for normal, roughness, height, AO, metallic, and packed mask maps.

## Added Research Delta: Rodin 3D / Hyper3D

Rodin should be researched as an AI 3D asset source, not as the terrain generator. The official Hyper3D API docs indicate:

- Generation is asynchronous: submit a task, poll status, then download generated files.
- It supports text-to-3D, image-to-3D, and multi-image generation.
- Multi-image mode can concatenate views of one object or fuse features from multiple objects.
- It exposes seed controls.
- It exports geometry formats including GLB, FBX, OBJ, USDZ, and STL in the documented generation API.
- It exposes material mode: `PBR`, `Shaded`, or `All`.
- PBR includes base color, metallicness, normal, and roughness textures.
- It exposes quality tiers such as high/medium/low/extra-low and a polycount override range.
- Rodin Gen-2 docs mention baked normals, HD texture maps, and 2K/4K texture tiers depending on package/tier.

Rodin integration should therefore be a replaceable provider behind a generic interface:

- `submit_external_asset_generation`
- `poll_external_asset_generation`
- `download_external_asset_package`
- `inspect_generated_asset_package`
- `validate_generated_asset_for_terrain`
- `ingest_external_asset_to_catalog`

Required validation before Rodin-generated assets can enter terrain:

- file format is allowed for the target pipeline
- mesh scale and axis conventions are normalized
- polygon count is within quality profile budget
- UVs exist and are non-degenerate
- PBR material maps are present or explicitly downgraded
- texture resolution fits the active low-spec/AAA profile
- topology is acceptable for static scatter or marked fallback
- collision proxy can be generated
- LOD or impostor strategy exists
- license/source metadata is recorded

Rodin must not be allowed to generate terrain heightfields, river systems, material weights, or scatter maps directly. It can generate rocks, props, ruins, roots, logs, hero plants, cave dressing, debris pieces, and other instanced assets after passing validation.

## Added Research Delta: Free / Usable Foliage and Prop Routes

The foliage route should be provider-neutral. The best practical options are:

- Built-in Blender Sapling Tree Gen for procedural tree prototypes and quick fallback trees.
- Open-source Blender add-ons such as MTree-style procedural tree generation where licensing and maintenance are acceptable.
- SpeedTree only as a reference or paid/proprietary route unless the user's license allows production usage.
- PlantFactory/Vue as a reference or source only if the current free/license state is verified before adoption.
- Quixel/Megascans/Fab for scanned rocks, logs, debris, stumps, surfaces, and ground materials where license terms fit the target engine/project.
- Rodin/Hyper3D as an optional generated-prop provider, never as the core terrain/scatter authority.

Every foliage/prop source must feed the same validation path:

1. Generate or import prototype asset.
2. Validate scale, axis, UVs, topology budget, PBR maps, texture resolution, collision proxy, LOD/impostor plan, wind profile, and license/source metadata.
3. Register prototype in `terrain_foliage_catalog.py` or `terrain_assets.py`.
4. Place only through `ScatterPointTable`.
5. Export prototype and instance data separately.

Target prop categories:

- tree variants by biome
- tall/short/dry/lush grass with height bands
- shrubs and bushes
- reeds, lily pads, algae, submerged grass
- logs, rotten logs, stumps
- vines, moss, mushrooms, flowers, ferns, clovers
- rocks, pebbles, gravel, talus, boulders, hero boulders
- path props, signs, fences, bridges, ruins, cave dressing, roots, debris

## Added Research Delta: Roads, Paths, Rivers, and Procedural Bridges

Roads and paths must become graph/corridor systems, not isolated terrain cuts. World Creator path/river spline exports, Unreal/Unity spline workflows, and Houdini curve/heightfield workflows all point to the same architecture:

- Store roads and paths as graph segments with stable ids.
- Preserve node-edge continuation metadata so roads and rivers continue into future terrain nodes.
- Generate corridor masks for road core, shoulder, ditch, embankment, approach transition, wear/dust, mud/wet edges, bridge approaches, and exclusion zones.
- Use hydrology data to decide bridge vs ford vs reroute.
- Use material stacks per path type rather than a single dirt color.
- Emit scatter exclusion and affinity masks along paths: no trees inside road core, grasses at edges, rocks/logs/debris only where allowed.
- Export splines/segments, masks, material layers, crossing metadata, and bridge specs.

The first implementation foothold is now present in `veilbreakers_terrain/handlers/terrain_path_contracts.py`. It adds `PathNetworkContract`, `PathSegmentContract`, and validation for deep-water crossings and procedural bridge requirements.

Bridge-specific rules:

- Deep water crossings must emit a bridge or ford contract.
- Bridge segments require span, clearance, material stack, approach transition, continuation edge, and water-crossing metadata.
- Bridges must preserve river flow clearance and not flatten the river into a fake road decal.
- Bridge approaches must blend road material into bridge material and back into road/path material.
- Node exits must record whether the segment continues on north/south/east/west so future nodes can connect seamlessly.
- Bridge scatter masks must block trees/large rocks on the deck, allow edge props only where safe, and reserve collision/navmesh clearance.

## Non-Negotiable Guardrails

- [ ] Every handler callable must have a row in `INDUSTRY_BEST_PRACTICE_CALLABLE_MATRIX_2026_04_26.csv`.
- [ ] Every modified callable must satisfy its matrix row's best-practice contract, setup rules, validation gates, anti-pattern blockers, and output artifacts.
- [ ] P0 matrix rows are blockers, P1 rows are required quality upgrades, and P3 rows must be regression-locked without weakening their current guarantees.
- [ ] No new one-shot terrain builder may generate map geometry directly unless it calls the canonical terrain pipeline and emits required manifests.
- [ ] No production foliage scatter may place mesh instances without a typed scatter point table.
- [ ] No production water body may be represented only by a flat mesh or single `water_mask`; it must include surface elevation and depth.
- [ ] No waterfall may pass QA without lip, plunge pool, foam, mist, wet-rock, downstream flow, and actual mesh/particle validation.
- [ ] No material pass may pass QA if layer weights do not sum to one per texel or if wet/deposit/talus/flow channels are ignored where available.
- [ ] No callable may be considered AAA-ready on grade spreadsheet claims alone; it needs direct behavior tests, dispatch evidence when exposed, and at least one integration proof if it affects terrain output.
- [ ] No asset provider-specific generation surface should be restored. The asset layer must remain provider-neutral and manifest-driven.
